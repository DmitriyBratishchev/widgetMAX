# Чат MAX через GREEN-API

**Статус:** ready-for-task
**Уровень:** эпик
**Дата начала:** 2026-09-29

## 1. Контекст

Тестовое задание (`.docs/requirements.md`): веб-чат для отправки и получения **текстовых**
сообщений в MAX через GREEN-API, внешний вид — по образцу https://web.max.ru/, интерфейс
максимально простой. Сценарий приёмки: ввод `idInstance` + `apiTokenInstance` → номер получателя
и новый чат → отправка → ответ получателя из MAX → ответ виден в чате.

Каркас SPA уже в `dev` (Vite + React 19 + TS, TanStack Query, Zustand, SCSS-токены, Vitest).
Ресёрч фиксирует проверенные факты об API, решения Димы и нарезку работы на задачи `WM-NN`.

## 2. Заметки: проверенные факты

Проверено 2026-09-29 запросами `curl` с **заведомо фейковыми** данными (`waInstance1101000000`,
`waInstance3100000000`, токен `test-token`). Поведение на живом инстансе отмечено отдельно.

### 2.1. CORS — прокси не нужен

- `GET https://api.green-api.com/waInstance…/getStateInstance/…` с `Origin: http://localhost:5173`
  → `Access-Control-Allow-Origin: *`.
- Preflight `OPTIONS` для `POST` с `Access-Control-Request-Headers: content-type` → `200`,
  разрешены `GET, POST, OPTIONS`, заголовок `Content-Type` разрешён.
- Preflight для `DELETE` (`deleteNotification`) → `200`, `Allow-Methods: GET, POST, OPTIONS,
  DELETE, HEAD`. Хост `3100.api.green-api.com` отвечает на preflight `204` и тоже разрешает
  `DELETE`.
- Вывод: SPA ходит в GREEN-API напрямую из браузера, прокси dev-сервера и прокси на деплое не
  нужны.
- **Подтверждено в браузере** (WM-01, 2026-09-29): форма входа на `localhost:5173` в headless Edge
  отправила `getStateInstance` на `https://3100.api.green-api.com` с фейковыми данными и получила
  401 — CORS браузер пропустил, форма показала «Неверный idInstance или apiTokenInstance».
- **POST из браузера подтверждён** (WM-02, 2026-09-29): форма нового чата в headless Edge
  отправила `checkAccount` (JSON-тело, preflight) на `https://3100.api.green-api.com` с фейковыми
  данными и получила 401 — форма показала «GREEN-API не принял учётные данные».

### 2.2. Хост `apiUrl` определяется первыми 4 цифрами `idInstance`

| Хост | Инстанс | Ответ |
|---|---|---|
| `3100.api.green-api.com` | `3100000000` | `401` — хост «свой», токен неверный |
| `3100.api.green-api.com` | `1101000000` | `404` — инстанс не с этого хоста |
| `7103.api.green-api.com` | `7103000000` | `401` |
| `1101.api.green-api.com` | `1101000000` | нет ответа — хоста не существует |
| `api.green-api.com` | `1101000000` | `401` — общий хост |

Вывод: `apiUrl` можно предложить автоматически — `https://{первые 4 цифры}.api.green-api.com`.
**Подтверждено на живом инстансе MAX** (WM-01, 2026-09-29): подставленный формой адрес совпал с
`apiUrl` в кабинете, вход прошёл. `idInstance` реального инстанса — **12 цифр** (фейковые
примеры выше — 10), валидация длину не ограничивает.
Работает ли общий `api.green-api.com` для **реальных** инстансов MAX — **не проверено**.

### 2.3. Ошибки — по коду статуса, тело не разбирать

- Неверный токен → `401`, **тело пустое** (`Content-Length: 0`). Клиент не должен вызывать
  `JSON.parse` на ответе с ошибкой.
- Инстанс не на этом хосте → `404` с HTML-страницей nginx.
- Ответ `401` пришёл с `X-RateLimit-Remaining: 0` и `X-RateLimit-Replenish-Rate: 1` —
  `GetStateInstance` ограничен 1 запросом в секунду (skill `green-api` §6). Кнопку входа
  блокируем на время запроса.

### 2.4. Не проверено (нужен живой инстанс Димы)

- ~~`stateInstance` у авторизованного инстанса MAX — ожидается `authorized`.~~ **Проверено**
  2026-09-29 (WM-01): авторизованный инстанс → `authorized`, до сканирования QR → `notAuthorized`
  (форма показала подсказку про QR-код). Частые повторы входа → `429`.
- ~~Ответ `CheckAccount` для номера без MAX (`exist: false`) и формат `chatId`.~~ **Проверено**
  2026-09-29 (WM-02, Дима): номер без MAX → форма показала «нет аккаунта в MAX», чат не создан
  (условие `!exist || !chatId`); номер с MAX → `chatId` из ответа принят, `SendMessage` на него
  дошёл в MAX. Точный вид поля (`""` при `exist: false`, числовая строка при `exist: true`) глазами
  не смотрели.
- ~~Совпадает ли `senderData.chatId` входящего с `chatId` из `CheckAccount`.~~ **Проверено**
  2026-09-29 (WM-03, Дима): ответ из MAX появился в чате, созданном по `chatId` из `CheckAccount`, —
  ключи совпадают (цикл кладёт в ленту только сообщения чатов из списка).
- Путь к тексту для `extendedTextMessage` / `quotedMessage` в MAX (skill `green-api` §4).
- Приходит ли `outgoingAPIMessageReceived` (эхо своей отправки) в очередь HTTP API.
- ~~Держит ли `ReceiveNotification` long-poll на `receiveTimeout`.~~ **Проверено** 2026-09-29
  (WM-03, Дима): пока у инстанса были выключены **все** уведомления (так у нового инстанса MAX по
  умолчанию; `webhookUrl` пустой), пустой ответ приходил за миллисекунды, и цикл без своей паузы
  слал сотни запросов в секунду, а ответы не приходили. После включения «…о входящих сообщениях и
  файлах» и «…отправленных с телефона» запрос висит `pending` 20 с (`receiveTimeout` — в секундах),
  сообщения приходят. Своя пауза 1 с после пустого ответа остаётся защитой от горячего цикла.
  Настройка — README, skill `green-api` §3.

## 3. Решения Димы

| # | Решение | Причина |
|---|---|---|
| Р1 | **Без роутера**: `App` выбирает экран (вход / чат) по признаку входа из стора `session` | два экрана, лишняя зависимость и SPA-fallback на деплое не нужны |
| Р2 | Учётные данные — в **`sessionStorage`** (persist Zustand) | переживают F5, стираются при закрытии вкладки; токен не лежит в браузере бессрочно |
| Р3 | **`apiUrl` подставляется из `idInstance`** (§2.2), пока пользователь не поправил поле сам | пользователь вводит 2 поля, как в ТЗ; нестандартный хост всё равно можно указать |
| Р4 | **Без Playwright / e2e** | «делаем по ТЗ»: Vitest + RTL на слои, сквозной сценарий Дима проверяет вживую |
| Р5 | Линтер oxlint, Prettier, LF | зафиксировано в `.claude/CLAUDE.md` §«Зафиксированные договорённости» |

### 5.1. WM-01 — Вход и сессия

Скоуп: транспорт `api/`, `GetStateInstance`, стор `session` с persist в `sessionStorage`, форма
входа (`idInstance`, `apiTokenInstance`, `apiUrl` с автоподстановкой), тексты ошибок (401 → неверные
данные, 404 → инстанс не найден на этом `apiUrl`, 429, сеть, `stateInstance` ≠ `authorized` →
причина), выбор экрана в `App`, кнопка «Выйти». Экран чата — заглушка-оболочка.

Одна фаза (все задачи эпика — одной фазой, решение Димы 2026-09-29): данные (клиент, сервис, хелперы, стор, хук входа) и UI
(кит `Button`/`Input`, `LoginPage`, выбор экрана в `App`, выход + тесты взаимодействий).

### 5.2. WM-02 — Новый чат и отправка

Скоуп: нормализация номера, `CheckAccount` → чат по числовому `chatId` (skill `green-api` §5),
`exist: false` → «нет аккаунта в MAX», стор `chat`, раскладка как у web.max.ru (список чатов
слева, лента справа, поле ввода снизу), `SendMessage`, исходящее сообщение в ленте из ответа
(`idMessage`), кнопка отправки недоступна при пустом тексте и во время отправки.

~~Открытое решение: хранить ли стор `chat` в `sessionStorage` вместе с сессией.~~ **Решено**
(Дима, 2026-09-29, старт WM-02): стор `chat` хранится в `sessionStorage` (ключ `widgetmax-chat`),
«Выйти» стирает его вместе с сессией. Причина: после F5 сессия остаётся, и без персиста пропали бы
чаты, а WM-03 показывает ответы только для чатов, открытых в UI, — ответ удалился бы из очереди.

Одна фаза: данные (хелпер телефона, сервисы, стор `chat`, хуки) и UI
(раскладка, список чатов, форма нового чата, лента, поле ввода).

### 5.3. WM-03 — Приём сообщений

Скоуп: один последовательный цикл `ReceiveNotification` → обработать → `DeleteNotification`
(skill `green-api` §3): удалять **каждое** уведомление, guard от двойного запуска в StrictMode,
остановка через `AbortController` при выходе, пауза при сети/429. Разбор уведомления в сообщение
(`incomingMessageReceived`, `outgoingMessageReceived`, дедуп эха `outgoingAPIMessageReceived` по
`idMessage`), только текст; события чатов, которых нет в UI, удаляются без отображения.

Одна фаза: хелпер разбора + цикл + подключение к `ChatPage`, с тестами порядка
receive/delete и остановки.

Решения на старте (2026-09-29, `.specs/features/WM-03-receive-messages/`): транспорт получил
опции `query` / `pathSuffix` — у `ReceiveNotification` параметр идёт после токена, у
`DeleteNotification` `receiptId` — сегментом после токена; `receiveTimeout = 20` с; ошибка →
пауза `1 → 2 → 4 → 8 → 16 → 30 с` со сбросом после успеха; guard StrictMode — `abort` в cleanup
эффекта; ~~ошибки опроса в UI не показываем (минимальный скоуп)~~. **Пересмотрено в WM-06**
(ресёрч `code-quality` §6 Р2): на 401/403 и на ошибке в коде цикл останавливается, над лентой —
плашка; сеть, 429, 5xx по-прежнему переживаются молча с паузами.

### 5.4. WM-04 — Сдача

Скоуп: доводка вёрстки под web.max.ru, узкий экран, состояния (пусто / загрузка / ошибка), README
(запуск, настройка инстанса, ссылка на деплой), публичный деплой (желательно по ТЗ), скриншоты.

~~Открытое решение: площадка деплоя (GitHub Pages / Vercel / Netlify).~~ **Решено** (Дима,
2026-09-29, старт WM-04, `.specs/features/WM-04-delivery/`):

- Деплой — **GitHub Pages** через GitHub Actions (`.github/workflows/deploy.yml`, push в `main` +
  ручной запуск). Причина: репозиторий уже на GitHub, отдельный аккаунт площадки не нужен. Сборка —
  с `base: './'`: относительные пути работают и под `/widgetMAX/`, и в корне; роутера нет — fallback
  не нужен (§3 Р1). Проверено `vite preview --base /widgetMAX/`: страница и ассеты — 200.
- Из отложенного в WM-02/WM-03 — **сортировка чатов** (новое сообщение поднимает чат в начало
  списка); индикатор статуса опроса — **нет**: ТЗ просит минимальный набор функций, ошибки опроса в
  UI не показываем с WM-03 (с WM-06 — кроме остановки цикла на 401/403 и ошибке в коде, см. §5.3).
- Вёрстка — по образцу web.max.ru на усмотрение исполнителя: две колонки на всю высоту, шапка в
  сайдбаре, аватар-кружок с двумя последними цифрами номера (имён нет), на узком экране (≤768px) —
  одна колонка и «Назад». Скриншоты — `docs/screenshots/`, только фейковые данные.
  Уточнено по скриншоту web.max.ru (Дима): без левой колонки навигации; лента и поле ввода — колонка
  700px, пузырь до 488px; поле ввода — «парящая» карточка над фоном, сообщения под ним не видны;
  фон чата — градиент (узор — бренд, не берём).

## 8. Известные проблемы

- `sessionStorage` читается любым скриптом страницы (XSS). Приемлемо: сторонних скриптов нет,
  текст сообщений рендерится как текст (`rules.md` §7).
