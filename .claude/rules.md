# WIDGETMAX — ЯДРО ДИРЕКТИВ

> Зонные знания — скилы `frontend-patterns` и `green-api`: тело подтягивается по релевантности.

---

## 1. СТРУКТУРА ПРОЕКТА (кратко)

```
src/          — React 19, TypeScript (api/, services/, hooks/, stores/, components/, pages/)
.docs/        — requirements.md (скоуп задания)
.research/    — ресёрчи: заметки, варианты, решения, разбивка эпика на задачи
.specs/       — templates/ + features/{WM-NN-задача}/ (spec.md, plan.md, tasks.md)
.claude/      — правила, скилы, хуки, команды
README.md     — описание и инструкция локального запуска (результат задания)
```

Одно SPA в корне репозитория. Внешний сервис — GREEN-API (инстанс MAX), бэкенда нет.

## 2. РЕСЁРЧ

Ресёрч — фаза **ДО** спеки. Триггеры: «обсудим», «поресерчим», «подумаем», «исследуй»,
«варианты», «как лучше», «давай разберём», «покопай», «сравни» → создать/обновить
`.research/{topic-name}/research.md` по шаблону из `.research/README.md` (команда `/research`).
**НЕ** создавать спеку и **НЕ** писать код, пока Дима явно не скажет «делаем» / «пиши спеку».
Статусы: `draft` → `in-progress` → `ready-for-task` → `archived`. Ресёрчи коммитятся,
изображения — рядом с `research.md`.

## 3. SPEC-DRIVEN DEVELOPMENT

**Любая нетривиальная работа начинается со спецификации.** В сомнениях → спек.

| Масштаб | Примеры | Что делать |
|---------|---------|------------|
| Тривиальное | стиль, текст, одна строка | сразу код, без номера и спеки |
| Малое | поле формы, fix на 2–3 файла | `spec.md` + код |
| Среднее | экран с логикой, метод API + хук + UI | spec → plan → tasks → код |
| Крупное | несколько экранов / методов API | эпик: ресёрч с разбивкой на задачи `WM-NN` |

```
[SPECIFY] → [PLAN] → [TASKS] → [IMPLEMENT] → [VERIFY]
 spec.md     plan.md   tasks.md   код + тесты   DoD check
```

- Шаблоны — `.specs/templates/`; каталог задачи — `.specs/features/{WM-NN-задача-kebab}/`.
- **Иерархия эпик → задача → фаза** (карта команд — `.claude/CLAUDE.md` §«Рабочий процесс»):
  эпик — ресёрч с таблицей задач; **задача** — свой `WM-NN`, своя спека и **своя ветка**;
  **фаза** — шаг задачи, **один коммит** в её ветке. Крупное в одну задачу не тащим.
- **Живые документы (накопительные).** `spec.md`/`plan.md`/`tasks.md` не замораживаются после
  планирования: новый критерий/скоуп → в `spec.md`; шаг/фаза → в `plan.md` **накопительно**
  (отмечать сделанное, не переписывать историю); статусы → в `tasks.md` по ходу. Выяснилось, что
  нужно поменять задачу или эпик (скоуп, критерии, разбивку, чек-лист сценариев), — правка в
  `spec.md` и/или ресёрч **в этой же фазе, до коммита**, в момент принятия решения.
- **Размер фазы** — примерно половина контекста чата вместе с тестами и отладкой; вторая половина
  — на правки по замечаниям. Контекст расходует не число файлов, а работа вокруг них (чтение,
  прогоны, разбор падений). Явно не влезает — сказать и предложить разрез, а не дотягивать молча.
- **СТОП-точки**: нет спеки → не планировать; нет плана → не кодить.
- VERIFY: пройти критерии приёмки `spec.md` с доказательствами, обновить статус
  (ЧЕРНОВИК → УТВЕРЖДЕНО → В РАБОТЕ → ЗАВЕРШЕНО).

## 4. РИСКИ И DOD

| Уровень | Критерии | Действие |
|---------|----------|----------|
| **SAFE** | Только UI, стили, локальное состояние | Работаем |
| **CAUTION** | Контракт запросов GREEN-API, очередь уведомлений, учётные данные | Сверка со skill `green-api`, тест на слой |
| **BLOCKED** | Поведение API не проверено, затронуты сборка/деплой | Сначала ресёрч |

Перед реализацией определить DoD: **команда** для проверки + **ожидаемый сигнал**.
Перед действием: что уже есть в кодовой базе (grep)? какой контракт меняется? риск сломать?

Уровни готовности: **VERIFIED** (DoD + доказательство) > **COMPLETED** (реализовано,
указано что не проверено) > **IN_PROGRESS** > **PROPOSED**.
Слова «работает / готово / исправлено» требуют доказательства (вывод теста, лог, скриншот).
Нет доказательства → понизить уровень заявления, а не формулировку.

Тесты зелёные ≠ сценарий работает. Сквозной сценарий из `.docs/requirements.md` (ввод
учётных данных → новый чат → отправка → ответ из MAX → ответ виден) проверяется вживую на
реальном инстансе — это делает Дима; сообщить ему, что именно проверить.

## 5. GIT И КОММИТЫ

**Всё локально, в конце — один PR.**

```
main                        — только то, что уже в GitHub; руками не трогаем
└── dev                     — интеграционная ветка, в неё сливаются задачи
    ├── feature/WM-NN-<kebab>        — задача (все её фазы — коммиты в этой ветке)
    └── fix/<kebab>  docs/<kebab>  chore/<kebab>   — разовые правки без номера
```

**Номер задачи `WM-NN`** — сквозной, по порядку работы: из таблицы эпика, а для задачи вне
эпика — следующий свободный (по `.specs/features/` и коммитам `[WM-NN]`). Задачу, у которой уже
есть ветка, коммиты или спека, не перенумеровываем. Мелкие разовые правки идут без номера.

1. Начало задачи: `/task-start` — `git checkout dev` → `git checkout -b feature/WM-NN-<kebab>`.
2. **Ветка = задача, фаза = один коммит** в ней: код + тесты + живые документы вместе. В `dev`
   не уезжает полуфабрикат — задача сливается целиком после последней фазы. **По умолчанию
   задача — одна фаза**, то есть один коммит `[WM-NN]` (`.claude/CLAUDE.md` §«Зафиксированные
   договорённости»).
3. **Доводка фазы — в тот же коммит** через `git commit --amend`, пока следующая фаза не начата.
   Началась — отдельный `fix(область): доводка ФN [WM-NN]` с причиной. `rebase` по фазовым
   коммитам не делаем.
4. Закрытие задачи (`/finish` на последней фазе): `git checkout dev` → `git merge --no-ff <ветка>`.
   `--no-ff` оставляет в истории PR merge-коммит на каждую задачу — ревьюер видит их границы.
   Слитые ветки **не удаляем** — остаются в репозитории (решение Димы).
5. По ходу работы **ничего не пушим**. Когда Дима скажет «отправляем» — выдать команду пуша
   `dev` в блоке кода; PR `dev → main` Дима открывает в GitHub сам.

Пуш, PR и любые операции с remote — **только Дима**: выдать команду в блоке кода и объяснить,
что она сделает.

Формат коммита: `<тип>(область): <описание на русском> [WM-NN]`
Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`. Область — зона изменений
(`chat`, `auth`, `api`, `ui`, `config`, `claude`), для сквозных правок — основная.
`[WM-NN]` — номер задачи; у разовых правок без номера его нет. **Без `Co-Authored-By`.**

Примеры:
```
feat(auth): форма входа и проверка инстанса через GetStateInstance [WM-01]
fix(api): удалять уведомление из очереди после обработки [WM-03]
chore(claude): обновить правила проекта
```

## 6. ТЕСТИРОВАНИЕ

1. Тесты для нового/изменённого функционала — вместе с кодом, не потом.
2. **По ходу работы — только точечно**: `npx vitest run <файл>`, `npm run typecheck` (`tsc -b`,
   оба проекта TS), `npm run lint`.
3. **Полный прогон — один раз за фазу, в `/finish`**: `npm run lint` + `npm run format:check` +
   `npm run build` + `npm run test:run`. Ни одна проверка не заменяет другую: `build` несёт
   свой `tsc -b` (он же `npm run typecheck`), `lint` (oxlint, `--deny-warnings`, правила по типам)
   ловит устаревшие API, потерянные промисы, правила React Hooks и `only-export-components`,
   которых не видят ни типы, ни тесты; `format:check` — Prettier. Локально —
   `npm run test:run -- --maxWorkers=2`, если машине не хватает памяти. CI (`ci.yml`) гоняет то же
   на PR и push в `dev`.
4. Сеть в тестах не ходит: GREEN-API мокается на уровне `services/`.
5. Приёмка поверх автотестов — `/task-check` (матрица по критериям `spec.md`).

## 7. БЕЗОПАСНОСТЬ

- **`apiTokenInstance` — секрет.** Не хардкодить, не класть в `.env` (переменные `VITE_*`
  вшиваются в бандл и уезжают на публичный деплой), не логировать, не показывать в URL
  приложения и в тексте ошибок. В ресёрчах, спеках и тестах — только фейковые данные.
- `console.log` в коммите запрещён; отладочный вывод — только под `import.meta.env.DEV` и без
  токена (в URL запросов GREEN-API токен стоит в пути — URL целиком не логировать).
- Ошибки API показываем пользователю человеческим текстом, без сырого тела ответа.
- Текст сообщений рендерится как текст (React-экранирование); `dangerouslySetInnerHTML` запрещён.

## 8. ЗОЛОТЫЕ ПРАВИЛА

1. **Скоуп — `.docs/requirements.md`**, только текстовые сообщения, минимальный UI
2. **Ресёрч → спека → план → код** — нет спеки → не планировать, нет плана → не кодить
3. **Тесты вместе с кодом** — не отдельно, не потом
4. **Только CSS Custom Properties** — никаких хардкод цветов и размеров вне `styles/tokens/`
5. **Серверные данные отдельно от UI-стейта** — skill `frontend-patterns` §«Состояние»
6. **Токен не утекает** — ни в код, ни в логи, ни в бандл, ни в документы
7. **Доказательства для заявлений** — «работает» = вывод теста или скриншот
